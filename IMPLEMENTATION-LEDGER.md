# Lepidy implementation ledger

Companion: [implementation plan](IMPLEMENTATION-PLAN.md). This file is the source of task status.

## Agent update rules

1. Pick a task whose dependencies are done. Claim it by changing status to in_progress and filling Owner with your task/agent identity and Started with an ISO date. Re-read before editing to avoid overwriting another agent's claim.
2. Never change another active owner's row without coordination. Dependencies refer to completed integrated work, not another branch's intention. Claim shared-schema/contract changes explicitly before concurrent edits.
3. Status values: todo, in_progress, blocked, done. Check the Done box only with status done. Blocked means a concrete missing decision, failed dependency, or external requirement; record the unblock condition.
4. Preserve IDs. Split oversized work into suffixed IDs (for example C08a) and update dependencies; keep the parent incomplete until all children pass. Do not reuse deleted IDs.
5. Before completion, integrate the change, satisfy the acceptance column, add automated integration coverage required by [TESTING.md](TESTING.md), run `npm run verify:local`, and append an evidence record. Set Finished and link the evidence heading from the row. Unit-only or manual-only verification cannot complete implemented behavior. Do not record planned tests as passed.
6. Evidence includes scenario IDs, changed paths, reused source revision/path, actual commands/results, exercised boundaries and local doubles, supported platforms actually run, remaining limitations and follow-ups. No secrets or private tokens.
7. Documentation preparation does not complete implementation tasks. All tasks below intentionally begin unchecked. Check a decision only when resolved, recorded and propagated to affected specs.
8. At handoff, update active rows and evidence, identify the next ready task and exact blockers. No elapsed-time or automatic percentage-based completion.
9. This ledger organizes work; it does not authorize deployments, purchases, messages, account changes or store submissions beyond the user's instructions.

Source keys S1–S7 and V1–V4 resolve in plan §4. Acceptance criteria are cumulative with plan §6. Dates and owners are blank until work starts.

## Evidence records

### C01a — One progressively enhanced form pattern

- Task / owner: C01a / `/root`
- Status / dates: done / 2026-09-06 to 2026-09-06
- Why this row exists: two defects in two days came from the same place, and the second one proved that guarding the pattern was not the same as removing it. A01's gate found a form submitting natively before hydration and losing the page; A02's gate found the *fields* losing what was typed for the same underlying reason. Both were guarded with a hydration gate, which works, and neither fixed the shape that produced them. The user asked for the shape to be fixed.
- Implementation delivered: the emoji administration form and the agent create form now post to server actions through `<form action={…}>` with `useActionState`, the way the sign-in, sign-up, consent and connections forms already did. Their fields are uncontrolled, so characters typed before hydration are still there when the form is submitted. This is now the only pattern in the codebase for a form that writes.
- **A form that cannot work before hydration must say so, not pretend.** The composer is client-state by nature — Enter-to-send, snippet mode, draft syncing — so it keeps the hydration gate and reports itself as not editable until it is ready. That is the honest half of the same rule, and `components/shell/use-hydrated.ts` now exists for exactly that case rather than as a general guard.
- **The idempotency key had to survive losing JavaScript.** It was generated with `crypto.randomUUID()` in the click handler, which does not exist before hydration. The server now renders a seed and the key is `agent:<seed>:<directory length>`, so it changes only when the directory does: resubmitting a form that failed is the same request, while a second successful create is a new one. A missing or malformed key is still refused rather than invented, because inventing one at the server would defeat the point of having it.
- **CSRF moved to a server-rendered hidden field.** It was read from `document.cookie` at submission time, which is a script. It is now rendered by the page that renders the form. The trade-off is real and worth stating: a token rotated in another tab after this page rendered will be refused until the page is reloaded, where the old code would have picked the new one up. That is the price of the form working without scripting, and the failure mode is a visible refusal rather than a silent one.
- Changed files: `app/(app)/emoji/actions.ts`, `app/(app)/emoji/page.tsx`, `app/(app)/agents/actions.ts`, `app/(app)/agents/page.tsx`, `components/shell/emoji-admin.tsx`, `components/shell/agent-directory.tsx`, `playwright.config.ts`, `tests/browser/productivity.spec.ts`, `TESTING.md` and this ledger.
- Integration scenarios: `FORM-INT-001` now runs with scripting switched off and creates an agent, has a namespace-violating handle refused with the error rendered, names a custom emoji, removes it again, and then finds the composer reporting itself as not editable. Its earlier form asserted only that nothing was lost; it now asserts the forms actually work, which is a stronger claim about a smaller surface. `EMOJI-INT-005` and `AGENT-INT-015` continue to drive the same surfaces with scripting on.
- Verification: `npm run verify:local` passed end to end with 343 Worker/D1/SQLite/crypto tests, 3 native Windows file-backed SQLite integration tests, 79 desktop/mobile browser tests, TypeScript, the production Next.js/OpenNext/Wrangler builds and zero production dependency vulnerabilities.
- **A harness instability was investigated and deliberately not 'fixed'.** Three `verify:local` runs during this work died in the middle of the browser suite: workerd logged broken pipes, wrangler's ProxyController reported `Network connection lost` and exited, and every remaining scenario failed with `ERR_CONNECTION_REFUSED`. **Playwright's worker count was lowered from three to two on the theory that it was capacity, and that theory was wrong** — at two workers the crash came *earlier* and took 45 tests instead of 21. The change was reverted rather than kept. What is actually established: it is not memory (14 GB free, no OOM kills); it is not concurrency; it has never reproduced in a standalone `npx playwright test` run (two full-suite runs and six isolated runs of the no-scripting test, all clean); and it has only ever happened inside a nested `npm run verify:local`. The last thing the worker logs before dying is `failed to get redirect response [Error: Network connection lost.]`, which is OpenNext's server-action redirect path. The remaining hypothesis is stdio or loopback pressure from the process nesting the gate adds, and the next person to hit it should look at `scripts/browser-worker.mjs` and the webServer stdio settings in `playwright.config.ts` rather than tuning worker counts. **A dead harness is not a result in either direction**; each of those runs was re-run rather than reported, and the run recorded below is one uninterrupted pass.
- Exercised boundaries and limitations: `setAgentBriefAction` keeps its object-argument shape because nothing submits it yet — the agent detail page that would is R05/C07 surface work — and it should become form-driven when that page is built. The message edit form and the forward dialog are opened by a click and therefore cannot exist before hydration, so they are unaffected. Scheduled-message and draft surfaces inside the composer inherit the composer's gate rather than the form pattern.

### A02 — MCP OAuth and connection management

- Task / owner: A02 / `/root`

- **A token names its workspace, and a prefix routes but never authorises.** Every minted secret is `lpd_<kind>_<workspace>_<secret>`, so a token endpoint with no session and no workspace in its path still knows which tenant to ask. The object then has to recognise the hash, so the prefix decides *where* a question is asked and never *what the answer is*. `MCP-RULE-001` proves the spelling parses exactly one way even though a base64url secret contains the separator, because a token that parsed two ways would be a token that routed two ways.
- **A token names its audience, and the resource server checks the audience it was actually reached at.** RFC 8707 resource indicators are mandatory rather than optional here. `MCP-INT-004` presents one workspace's token at another's object, and presents it at its own object while claiming the other's audience; both are refused, and the token still works where it belongs. - **A rotated refresh token presented again ends the connection.** A leaked token and a client that lost the response to its own rotation are indistinguishable from the server, so the safe reading is the first: the connection dies and the person reconnects. `MCP-INT-003` proves the current pair dies too, not only the replayed token, and that the reason reaches the audit. Refusing another client's use of a token is deliberately *not* treated as a leak, and the same test proves the connection survives that.
- **Removing somebody cuts their connections off with nothing to revoke.** Membership is re-checked live inside the object on every call, so there is no revocation sweep to run and no cache to wait out. `MCP-INT-005` removes a member and shows the very next call fail, with neither the token expired nor anything revoked.
- **Consent is the only decision a person makes, so everything else is decided before they see it.** The screen renders only after the request has been validated against the registry and the workspace, and the action validates it again from scratch rather than trusting its own hidden fields — between rendering and submitting, a registration can change and a membership can end.
