# Lepidy implementation ledger

Companion: [implementation plan](IMPLEMENTATION-PLAN.md). This file is the source of task status.

## Agent update rules

1. Pick a task whose dependencies are done. Claim it by changing status to in_progress and filling Owner with your task/agent identity and Started with an ISO date. Re-read before editing to avoid overwriting another agent's claim.
2. Never change another active owner's row without coordination. Dependencies refer to completed integrated work, not another branch's intention. Claim shared-schema/contract changes explicitly before concurrent edits.
3. Status values: todo, in_progress, blocked, done. Check the Done box only with status done. Blocked means a concrete missing decision, failed dependency, or external requirement; record the unblock condition.
4. Preserve IDs. Split oversized work into suffixed IDs (for example C08a) and update dependencies; keep the parent incomplete until all children pass. Do not reuse deleted IDs.
5. Before completion, integrate the change, satisfy the acceptance column, add automated integration coverage required by [TESTING.md](TESTING.md), run `npm run verify:local`, and append an evidence record. Set Finished and link the evidence heading from the row. Unit-only or manual-only verification cannot complete implemented behavior. Do not record planned tests as passed.
6. Evidence includes scenario IDs, changed paths, reused source revision/path, actual commands/results, exercised boundaries and local doubles, supported platforms actually run, remaining limitations and follow-ups. No secrets or private tokens.
7. Documentation preparation does not complete implementation tasks. All tasks below intentionally begin unchecked. Check a decision only when resolved, recorded and propagated to affected specs.
8. At handoff, update active rows and evidence, identify the next ready task and exact blockers. No elapsed-time or automatic percentage-based completion.
9. This ledger organizes work; it does not authorize deployments, purchases, messages, account changes or store submissions beyond the user's instructions.

Source keys S1–S7 and V1–V4 resolve in plan §4. Acceptance criteria are cumulative with plan §6. Dates and owners are blank until work starts.

### O01a — Retention sweeps, R2 reclamation and workspace purge

- Task / owner: O01a / `/root-o01`
- Status / dates: done / 2026-09-10 to 2026-09-10
- Delivered: workspace deletion, an idempotent resumable purge, and the hourly reclamation that gives attachment storage back. O01 was split first, because removing data and moving it fail in opposite directions — one is irreversible and the other must not resurrect authority — and **O01b owns export and restore**, so the parent O01 row stays incomplete until it passes.
- **The whole task is shaped by one asymmetry: a purge cannot be undone.** Every other destructive thing in this product is recoverable — a revoked grant can be granted again, an offboarded member re-invited, a deleted message leaves a tombstone. This removes a company's conversations, their attachments and their credential ciphertext, and no authority afterwards brings any of it back. So the gate is deliberately awkward: owner role, **the workspace's own name typed out**, and a verified gesture. The name rather than the word "DELETE", because "DELETE" is muscle memory within a week and the name of the thing being destroyed cannot be typed absent-mindedly.

### P03b — Web push transport and approval delivery

- Task / owner: P03b / `/root-p03`
- Status / dates: done / 2026-09-10 to 2026-09-10
- Delivered: a working web push transport — VAPID identity, per-browser subscriptions, RFC 8291 encryption, an outbox dispatcher for message and approval pushes, and the authorised render path that decides what a device may display. With this the parent P03 row is complete.
- **A push payload carries identifiers, never words.** The payload is encrypted end to end, so the push service cannot read it — but the *device* renders it on a lock screen, and what appears there is somebody else's workspace. So the service worker fetches the text to display with the viewer's own session, which means **visibility is decided at the moment of display rather than the moment of send**: somebody removed from a room in the seconds between gets nothing, and a deleted message becomes unrenderable after its push has already gone out. That is C06's decision, not this task's — it deliberately wrote a metadata-only outbox and left transport here — so `assertMetadataOnly` checks the object actually being encrypted and refuses `title`, `body`, `credentialName`, `reason` and `message` by name. A better lock-screen preview is exactly the change that would quietly undo it.
- **The cryptography is real and is proven by decrypting it back.** The `aes128gcm` body's header is asserted byte by byte — a 16-byte salt, the record size, the key length, the sender's key — because that is where interop with a real push service breaks; and the record is then opened from the *receiver's* private key, because a round trip is the check that the key schedule is right and a vector recalled from memory would not be. The ephemeral key is per message, so anybody who ever recovered one could not read every push sent to that subscription. The VAPID token is ES256 with a raw `r‖s` signature rather than DER, which is the classic way a token is rejected by every push service with an unhelpful 401.
- **What the transport refuses.** A subscription over plain HTTP, one carrying credentials or a fragment, and one whose key is the wrong length — the last of those would otherwise fail inside an outbox retry loop with nothing to point at. A VAPID token is scoped to the push service's **origin** rather than the endpoint, because a token naming the endpoint would tell any service that logged it which subscription it was for. A push endpoint that redirects is never followed. And `404`/`410` **delete** the subscription: a reinstalled browser or a revoked permission leaves an endpoint that will never work again, and retrying it forever is how an outbox fills with work that cannot succeed.
- **A deployment with no key has no push transport, and says so.** Not a retry — a deployment will not grow a key between now and the next backoff — and not a silent success either. The outbox entry dead-letters with a readable reason, and `/api/push/key` answers 503 so the browser can tell somebody this deployment cannot push rather than leaving them to grant permission and wait forever for a notification nothing will send.
- **Two defects were found while proving it, and the second is the significant one.** First, the render test's premise was wrong rather than the code: a public room *is* visible to every member, so the negative case had to be a private room. Second, and a real gap: **offboarding did not remove push subscriptions.** The table has `ON DELETE CASCADE` on `members(id)`, but offboarding keeps the member row as a directory tombstone so old messages retain their attribution — so the cascade never fires, and a former member's phone would have kept receiving notifications about a workspace they were removed from. That is precisely the failure the tombstone is careful not to be. It is now an explicit delete on any non-active status, with a scenario that proves it.
- Smaller decisions worth recording. A subscription is **one row per browser**, because somebody signed in on a laptop and a phone has two and an approval must reach whichever they are holding; re-subscribing the same browser replaces its row rather than accumulating a dead endpoint; and an endpoint **moves to whoever is now signed in**, because a shared machine would otherwise send one person another's notifications. Unsubscribing is idempotent, because a request to stop being notified must never fail for having already been carried out. One reachable browser counts as delivered, since retrying because a second device was asleep would send the first a duplicate. And an approval whose five minutes have already run out is not sent at all — being asked to decide something already decided is how a person learns to ignore the notification that mattered.
- Changed files: `src/domain/web-push.ts`, `src/cloudflare/web-push.ts`, `src/shell/push-context.ts` (all new); `src/cloudflare/workspace.ts` (subscriptions, the render method, the dispatcher, the offboarding delete); `src/cloudflare/workspace-migrations.ts` (workspace schema v34); `src/types/cloud-runtime-env.d.ts`; `app/api/push/{key,subscribe,render}/route.ts` (new); `public/sw.js` (the `push` handler); `components/shell/notification-permission.tsx`; `app/(app)/inbox/page.tsx`; `tests/{web-push,push-delivery}.test.ts` (new), `tests/browser/pwa.spec.ts`, `tests/workspace.test.ts`; `README.md`; `TESTING.md` and this ledger.
- Reused design: the subscription shape and the encryption follow RFC 8291 and RFC 8188 directly. `notificationText` is the TypeScript counterpart of P01a's Rust notification sanitiser — the same argument (control characters, bidirectional overrides, a bound counted in characters) applied at the other end of the same product, because an agent-written reason reaching a lock screen is the same problem as one reaching a desktop notification. No reference code was copied and no new dependency was added.
- Automated evidence: `PUSH-RULE-001–005` and `PUSH-INT-001–004` in `tests/web-push.test.ts`; `PUSH-INT-005–010` in `tests/push-delivery.test.ts` against real workerd Durable Objects and SQLite; `PWA-INT-006–008` in the browser suite for the subscription boundary.

- **The asymmetry everything here follows from.** A Lepidy desktop build supervises a process holding injected credentials, and it replaces itself over the network. An unsigned installer is a program nobody can attribute; an unsigned update is one nobody can verify, delivered by a mechanism designed to run without asking; an update installed while a harness runs leaves a process tree with injected credentials and no supervisor. Each of those is a refusal in the build or a fixed ordering in the code, never a note in a runbook.
- **The gate refuses.** `lepidy-bundle-gate` runs before `tauri build` and exits non-zero when the environment cannot sign what it is about to produce: the updater key pair always, a Windows certificate thumbprint on Windows, and a Developer ID **plus** notarisation credentials on macOS — signing without notarising ships something Gatekeeper still will not open, which reads as a broken app rather than a missing step. Linux requires no code signature and the gate says so rather than inventing a requirement. Three properties matter as much as the list: it checks *presence*, not validity, because only the platform's tooling can judge a certificate; it **names variables and never reads their values**, so a failed build cannot put a signing key into a build log; and an empty variable is not a credential, which is the CI-fork case where every secret name is defined and none is populated. `--unsigned` builds for the current machine and says loudly that what it produced must not be published.
- **The direct build carries the injection engine.** PRD §10.1 makes the direct download the full product, so the bundle ships `lepidy` and `lepidy-agentd` as sidecars and the gate refuses if either is undeclared or unstaged — a bundle without them installs an application that cannot inject a credential, which nobody notices until `lepidy run` on a fresh machine. The declaration lives in `src-tauri/bundle.direct.json`, merged at bundle time, for two reasons: Tauri validates `externalBin` when the crate is **compiled**, so declaring sidecars in the base config would make `cargo check` — which the local gate runs every time — require a release build of the CLI; and §10.1's split between a direct build that carries the engine and a store build that cannot is exactly the shape a per-variant config file will need. **P02 owns the store variant.**
- **No key, no updater.** The verifying public key is compiled in from the environment, and a build given none registers no updater at all rather than one that trusts whatever answers the endpoint. A key read at runtime would be a key anybody who can write a file beside the application can replace, which is the whole attack the signature exists to stop; the committed `pubkey` is deliberately empty. Endpoints are HTTPS and none of Tauri's three `dangerous…` escape hatches is taken — plain HTTP would not let somebody forge an update, but it would let them see which version every machine in a company runs and withhold the release that fixes something.
- **The runner stops before the install, and a person chooses.** Checking is automatic because nobody can act on an update they were never offered; downloading and installing is a tray item, because this is a tray-resident supervisor and restarting it silently would stop a machine answering for somebody's agents at a moment nobody chose. The label carries the consequence — *"Restart to update to 0.2.0 (stops the runner)"* — because that is what a person supervising agents needs before they choose it. The ordering is asserted from the source, not merely written: `prepare_to_install` strictly precedes `install_pending_update`, since stopping afterwards would be stopping nothing. **No command reaches any of it**, and the pending update is a module-private slot with no accessor.

The fix declares the command surface to the ACL in `build.rs` and grants each command by name. The list now lives in three places — the invoke handler, the build script and the capability files — and `NATIVE-INT-001`/`003` assert all three agree and that every registered command is granted. Three places is more than one, but each is a place somebody would have to deliberately add a command to.

### P01a — Desktop presence: deep links, notifications, badges, kill-switch hotkey and offline fallback

- Task / owner: P01a / `/root-p01`
- Status / dates: done / 2026-09-09 to 2026-09-09
- Delivered: [the desktop presence contract](docs/desktop-presence-contract.md) and the four modules behind it. P01 was split first, because what the shell *does* while running and how it is *built and updated* fail in completely different ways and only one of them can be exercised without a signing identity; **P01b now owns signed direct builds, the updater and the WebdriverIO Tauri GUI harness R03 deferred**, and the parent P01 row stays incomplete until it passes.
- **The premise this task adds to R03's.** R03's is that the window renders content written by agents and by strangers. P01a's is sharper: **a registered URL scheme is an entry point into this process from the entire operating system.** Any web page can navigate a browser to `lepidy://…`, any message can contain one, and the platform hands it over without asking anybody. So a deep link is treated exactly like a message body, and the destination a notification carries goes through the *same* parser — one place decides where a click can lead, whoever caused it.
- **A deep link names a place, never a URL.** `deeplink::parse` returns a `Destination` from a closed set and the shell builds the address itself from the trusted origin plus that destination's path. No branch anywhere navigates to a string a link supplied, which is what makes `lepidy://open?next=https://evil.test` a parse failure rather than a redirect. A query, a fragment, any percent-encoding, a backslash, `.`/`..`, an over-long segment and an empty authority are each refused outright rather than sanitised — nothing accepted needs an escape, and a decoder here is the standard place `%2e%2e%2f` gets in. An unknown destination is refused and reported rather than quietly opened at the home page, because a link that silently went somewhere else makes a mistyped or hostile link indistinguishable from a working one.
- **No verb does anything.** There is no `lepidy://approve/…`, `lepidy://stop` or `lepidy://release/…`; every member of the set shows a page. A link that could approve would be an approval anybody could cause by getting one click, and §8.6's whole argument is that the person decides at a surface they trust. That rule is asserted as its own test, because the temptation to add an action arrives with the first notification somebody wants a button on.
- **A notification cannot stop being one line of text.** Control characters become a single word break, bidirectional overrides are removed rather than escaped — they reorder the characters *around* them, so a message body can rewrite how the title beside it reads — whitespace runs collapse, and length is bounded here rather than by the platform, counted in characters so a Japanese preview is not cut to a third of a Latin one. Nothing legible is a refusal, because a notification with an empty title is a blank popup carrying this product's icon and that teaches people the icon means nothing.
- **The badge is a count.** `badge_label` takes a number and returns digits, `"99+"`, or nothing; `badge_count` clamps identically so the dock and the tray never give two answers. There is no interface anywhere that puts a string in a badge: a badge whose contents came from a message would put a stranger's characters into the operating system's own chrome, where no sanitiser of ours sits between. Zero clears rather than showing a nought.
- **One global chord, and it stops.** §10.4 gives the kill switch four independent paths so no single one being unavailable is safety-critical; the hotkey is the desktop app's fastest, working with the window closed or on a machine whose tray the desktop environment declined to render. Exactly one shortcut is registered, its action is fixed to the supervisor's stop, and no page, link or file can point it elsewhere — a hotkey rebindable to *start* would be a machine that begins answering for somebody's agents because of a keystroke in another application. The chord is chosen on the machine (`LEPIDY_KILL_SWITCH`, default `CommandOrControl+Alt+Shift+K`); a mistyped override is fatal rather than silently replaced by the default, a chord with no modifier beyond shift is refused because `Shift+K` is how a person types a capital K, and reserved platform chords are refused by name. **A failed registration is reported and names the tray, the CLI and the web app**, because a kill switch that is silently not registered is a kill switch that does not exist and the moment somebody discovers that is the moment they needed it.
- **The offline fallback says what is actually true.** The runner holds its own outbound socket and has never needed this window, so "my laptop cannot reach the workspace" and "my agents have stopped" are different facts; the fallback's text is generated natively from the supervisor's own state and reads differently for running, stopped and exited. Only a load that never finished puts the window there — an HTTP error or a sign-in redirect is the workspace talking, and replacing that with "you are offline" would name the wrong problem. Twelve seconds of grace, then a doubling retry capped at five minutes, with the attempt count surviving the give-up so a laptop shut for a weekend comes back to a window still trying and a workspace genuinely down is not retried by every desktop in a company twice a second.
- **The fallback page has no native privileges, deliberately.** It is served from the application's own scheme, not the trusted origin, so `require_trusted_caller` refuses every command to it — including `runner_stop`. The whole reason the origin check is worth having is that it has no exceptions, and a local page that could stop the runner would be a local page worth navigating somebody to. The navigation guard admits exactly that one document, by exact host and exact path, and being admitted is not being trusted; the fallback's text names where the stop actually is instead.
- **The release build now opens on the workspace**, closing the README's standing "release builds show the bundled connection screen" gap, and `grant_workspace_capability` is the join that makes that safe: one window, remote-only, the same seven window-chrome permissions the checked-in file grants loopback, given to the one origin `TrustedOrigin` already validated. It cannot admit a second origin because there is only ever one, and a test asserts the two lists are identical. The three new plugins are **Rust dependencies, not granted capabilities** — no page can register a global shortcut, claim a scheme, or raise a notification that skipped `presence::prepare`.

### V08 — Agent onboarding and leak prevention

- Task / owner: V08 / `/root`
- Status / dates: done / started 2026-09-08, finished 2026-09-08
- Acceptance: MCP instructions and hints that steer a harness away from disclosure; the skill, hooks and `init` material an agent is onboarded with; the scan and canary design; hook behavior that is explicitly non-authoritative; and real-harness anti-circumvention evaluations — all satisfied and exercised by automated local integration coverage.
- Implementation delivered, as four layers with four different costs. **Layer 1** is the MCP server's `initialize` instructions: one authority sentence plus `VAULT_INSTRUCTION`, budgeted at eighty tokens and asserted by a test, because it is the only text every session pays for and the failure mode is somebody growing it into a manual. **Layer 2** is tool descriptions that say what will not happen, a new OAuth-scoped `credential_hint` tool that turns a shell command into the exact `lepidy run --with … --` rewrite, the `use` command and `canary` flag now carried on every listing, and V03's existing denial hints. **Layer 3** is `plugin/lepidy/skills/lepidy/SKILL.md`, embedded in the CLI binary so the skill can never be a different version from the tool it documents. **Layer 4** is `lepidy hook pretooluse`, the Claude Code `PreToolUse` hook, with five ordered rules and first-match-wins. `lepidy init` installs the MCP entry, the skill and the hook, and reports what it deliberately did not touch.
- Leak prevention delivered in two shapes with two threat models. A **scan target** is a SHA-256 digest of a credential value bound to workspace, credential and version, plus its length, computed by the client that sealed the value and served only over the signed device transport to a member already holding a verb on that credential. `lepidy scan <path|->` walks text a window at a time and matches locally, so the value never leaves the vault; it is wired into a `pre-commit` hook. A **canary** is a deliberately fake credential whose value is generated locally by `lepidy add --canary`, never typed and never printed, and whose public marker lets the workspace recognise it in content it already receives. A message, MCP tool argument or proxied request body carrying a canary marker is refused **before the write**, recorded as a durable trip with no excerpt, appended to the audit chain as `vault.canary_tripped`, and reported to that credential's custodians as a direct message from `@a.vault`.
- **The hook is advice, never the boundary**, and that is stated in the module, the plugin README, the skill, the harness contract §9, `TESTING.md` and the CLI usage text. ### R01 — Headless runner and local policy

- Task / owner: R01 / `/root`
- Status / dates: done / 2026-09-07 to 2026-09-07
- Delivered: [the local runner contract](docs/local-runner-contract.md), the wake transport D03 specified and deliberately did not build, and `lepidy-agentd` — the daemon a person runs on their own machine. The rule the whole task is arranged around: **the workspace decides *that* there is work; the machine decides whether, how often, how many at once, for how long, and what actually runs.**
- The wake frame carries the D05a trigger and nothing else — workspace, agent, device, the opaque *name* of a preset the machine already registered, that preset's revision, and a request id. There is no field for an executable, an argument, a working directory, an environment mapping or a permission posture, so there is nothing to smuggle one into, and an unknown key is a hard refusal of the whole trigger on both sides rather than a field that gets ignored. The workspace builds every frame through `parseRemoteLocalAgentTrigger` on the way out, so a field added here in future has to be added deliberately to the file whose purpose is refusing remote launch configuration; the runner parses it through a Rust mirror on the way in, because the guarantee only holds at the narrower end.
- Outbound only. The runner dials the workspace and the workspace answers on the socket the runner already holds, so a laptop behind NAT needs no open port, no inbound rule and nothing reachable from the internet; there is no code path by which a workspace initiates a connection to a machine. The upgrade carries the same F05 signed envelope as every other device endpoint, and because Next's own documentation is explicit that a Route Handler cannot hold a WebSocket ("the connection closes on timeout, or after the response is generated"), it is answered in the Worker entry before Next sees the request, with identity taken from the verified claims rather than any header the caller supplied. **A socket is not a registration**: an unregistered device, another member's device and a superseded runner epoch each get a 409.
- One device per agent, deliberately. Registering *moves* an agent and never quietly shares it, because two machines both deciding they answer is how one mention gets worked twice — and the queue's leases would then be the only thing between a duplicate and a duplicated side effect. The displaced device is named in the response and sent a stop; a registration with an epoch below the stored one is refused so a restarted process cannot reclaim agents a newer one took.
- Wakes cannot be lost, only delayed. Each is written in the same transaction as the queue row it announces and delivered only after that transaction commits — a mutation that rolls back delivers nothing, which needed a staged-then-flushed path in `commitMutation` rather than a send inside the transaction. Delivery is best effort and durability is not: an undelivered wake waits in `runner_wakes` until the machine reconnects, and the runner's own depth check covers the case a frame was sent to a socket that then died. Repeated work collapses into one pending wake, because a wake says *there is work*, not *there is this work*.
- The runner's own clock is what closes the race D03 left open by refusing a parked wait. The daemon asks the queue on every connection before waiting for anything, after every process exit, and on an idle timer clamped between one minute and one hour so a preset cannot turn it into polling. The socket's read timeout *is* that timer, so no second thread holds a clock. Two of these — the check on connect and the check after exit — were missing in the first implementation and were found by the integration scenario that stages work with no wake at all.
- Local brakes, in an order that is itself the contract: stopped, then unknown preset, then stale revision, then concurrency, then cooldown. A stop outranks everything because it is the one about authority. A wake storm, a mention loop and an agent that answers itself arrive looking identical and are all stopped by the last two rules — thirty wakes in a moment cost one process, measured.
- Stopping is durable first and a frame second: the durable half is that the agent's next bounded call is refused, and the frame is what makes it prompt. Pause, archive, delegation revoke and reassignment each send one; `releaseRunner` lets an owner stand a machine down **with the machine unreachable**, which is the case they most need it for. A stop kills the *tree* rather than the process the daemon happens to know about — its own process group on Unix, `taskkill /T` on Windows, terminate then kill after a grace — because a harness left alive after the thing that authorised it is gone is still holding injected credentials.
- Launch configuration lives in `$LEPIDY_HOME/presets.json` and nowhere else, behind two gates: the file must be owner-only and owned by the user running the daemon, checked on **every load** rather than only on write, because a file created correctly and later opened up is exactly what a write-time check misses; and editing it requires unsealing the local keystore, so a daemon that has been reached over the network cannot change what it runs. ### D03 — MCP waiting and harness spike

- Task / owner: D03 / `/root`
- Status / dates: done / 2026-09-07 to 2026-09-07
- Decision delivered: [the MCP waiting and harness contract](docs/mcp-waiting-and-harness-contract.md). **There is no parked wait.** No tool call blocks, nothing is held open while an agent is idle, and `agent_next` on an empty queue answers immediately with no item. A harness that waits does so on the runner's own clock; a wake arrives on the runner's outbound socket; and a wake that never arrived is closed by one queue-depth check on connection and on process exit.
- Why the obvious alternative is refused, recorded because it is obvious: a blocking `agent_next` is one line in a client and removes the need for a wake transport, but it prices idleness like activity — a Durable Object request held for the whole idle period, on a product whose free tier is "unlimited agents", so cost would scale with how many agents a customer creates rather than with the work they do. It also makes stopping hard, because the kill switch, a revoked delegation and an offboarded owner all have to reach an agent mid-wait, which needs a second channel — the socket the park was meant to avoid. And it hides lost wakes rather than preventing them: a parked call still ends on a timeout, a redeploy or a blip, so the reconnect path exists either way and is better exercised constantly than only during incidents.

A parked wait would appear in that table as one call orders of magnitude longer than the rest, and `MCP-WAIT-INT-001` asserts that none is, so the property stays proved rather than remembered. These establish shape and magnitude on a developer machine, not production latencies, which O02 owns.

### V05 — Capture, import and execution ergonomics

- Task / owner: V05 / `/root`
- Status / dates: done / 2026-09-07 to 2026-09-07
- Capture delivered: `lepidy capture NAME -- command` runs a command and stores its standard output as a new credential, so a token an agent mints never passes through the agent's own context — the alternative shape, a tool taking the value as an argument, puts the secret in the transcript before it reaches the vault and is what makes a credential swap possible. It is create-only, bounded at 64 KiB, refuses to store anything when the command fails or prints nothing, and lands on the most restrictive policy there is: inject-only, ask-every-time, no TTL. What it creates arrives **switched off**, with the program that produced it recorded, and stays unusable until a custodian confirms it with the same verified gesture that switches any other protection back on. An agent can create a credential this way; it cannot make one usable.
- Import delivered: `lepidy import PATH` seeds the vault from a `.env`. Create-only, so an existing name is reported and skipped rather than overwritten. Every skipped line says which line it was and why. No value is ever printed — not in a dry run, not in a summary, not in an error; lengths are, because a length is what justifies the short-value warning and is not itself the secret. The source file is left exactly where it is unless `--shred` is given, and `--shred` refuses to run when anything was refused, because removing the source after a partial import loses what did not make it.
- Execution ergonomics delivered: `--all-tagged TAG` injects a whole tagged group under one request and therefore one approval card; `--with-template SRC:PATH` resolves `${lepidy:NAME}` placeholders into an owner-only file removed when the command exits, leaving `${HOME}` and every other template-looking thing untouched; and a structured credential — one record carrying the five parts of a database credential — expands into one variable per field, each of them scrubbed from the child's output.
- Rotation delivered: a `rotateAt` date on a credential with a nag a week before rather than after, badged in the vault list and stated on the credential page; and `lepidy rotate NAME`, which re-seals the value as a new version under a new key. ### A04 — Delegations and session tokens

- Task / owner: A04 / `/root`
- Status / dates: done / 2026-09-06 to 2026-09-07
- Implementation delivered: owner-issued agent delegations and short-lived opaque runner-session credentials. A delegation binds one current owner, one agent, an optional channel subset, credential/delivery/project allowlists, spend ceilings, a write rate and a maximum lifetime. A session further binds one device id, runner epoch, preset revision and exact MCP capability set; only its SHA-256 digest is persisted, its credential rotates every 15 minutes, and its absolute lifetime is at most eight hours and never longer than the delegation.
